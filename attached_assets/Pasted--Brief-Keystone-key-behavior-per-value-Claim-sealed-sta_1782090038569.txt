## Item 1 — Keystone = the KEY BEHAVIOR within a value (build it properly)
Correct definition (from owner): keystone is NOT about ranking the values. Within a single value (standard), the user marks ONE of its 3–5 evidence behaviors as the KEY behavior — the truest signal of that standard. Each value has its own keystone behavior.

Build:
- Add a keystone marker on each evidence behavior chip in **Name the Standards** (e.g. a ★ on each `na1-m4-ns-evidence` chip). Tapping it marks that behavior as the value's keystone; tapping a different behavior moves the keystone; one keystone per value. Keystone is OPTIONAL but encouraged (a value is still valid without one).
- Add a real data field on the cluster, e.g. `keystoneBehaviorId` (the behavior id within that cluster's `behaviorIds`). Persist it; migration-safe (older values simply have none).
- Remove / re-point the dead "★ Keystone: not set" display in Rank: keystone is a property of a behavior within the value, not of the value's rank. It should NOT show as an unsettable label on the rank rows. If useful, the value's keystone behavior MAY be shown (read-only) in Rank / the pressure-test for context (see Item 3) — but the SETTING happens only in Name the Standards.
